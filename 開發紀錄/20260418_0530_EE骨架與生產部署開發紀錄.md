### 3.2 Deploy 安全漏洞修復

在推 CE Phase 1 code 到生產前，發現現有 `deploy_to_nas.py` 有嚴重問題：

- `IGNORE_DIRS` 只排 `venv / node_modules / build / __pycache__`
- **沒排** `license.key` → 會把本機測試用的 license.key 推到生產伺服器，讓偽造的 Enterprise 狀態啟用
- **沒排** `.env` → 會把本機開發 DB 憑證推覆蓋生產環境
- `*.pem` 也沒排 → 私鑰風險

修正（commit `75010f0`）：

```python
IGNORE_DIRS = {'venv', 'node_modules', 'build', '__pycache__', '.pytest_cache', '.git', 'license_keys'}
IGNORE_EXTS = {'.pyc', '.pyo', '.pem'}
IGNORE_FILES = {'.env', '.env.local', '.env.development', '.env.development.local', 'license.key'}
```

另外同步補 `Develop/backend/.dockerignore`：

```
license.key
license_keys/
*.pem
```

即使 deploy 腳本失守，Docker build 階段也會再擋一次。雙重保護。

## 四、關鍵設計決定

### 4.1 為什麼 EE 不用 fork workflow？

考慮過 GitHub-style fork + PR，但：
- Fork 會把 EE 本身的 commits 混進 CE 流量（追不乾淨）
- EE 是 private repo，對 CE 沒有「上游 PR」的需求
- `upstream` + `origin` 的 manual sync 更透明、責任更清楚

### 4.2 為什麼 EE 不能改 CE 檔案？

從開發體驗考量：
- CE 每次更新都得重新合併 EE 的修改 → 維護成本線性增長
- 如果 EE 改了 `app/routes/auth.py` 加 SSO 判斷，CE 也改 auth → 100% 衝突
- 正確做法：CE 先加 hook 點（如 `plugin.register_auth_adapter()`），EE 在 `app/ee/sso/` 實作 adapter

目前已建立的 hook 點：
- `register_router(router, prefix, tags)` — 動態路由
- `register_startup(fn)` / `register_shutdown(fn)` — lifespan hooks
- `register_menu(parent, code, label, icon, order)` — 動態選單（Phase 3+ 用）

未來需要時再擴充更多 hook。

### 4.3 為什麼 deploy 不用 git pull？

看到生產環境 `/home/porsche/ap.base/` 不是 git repo，原因推測：
- 歷史遺跡：可能最早是手動 rsync
- 避免 `.git` 目錄佔空間
- Production 環境不需要 git 歷史

繼續沿用 `deploy_to_nas.py` 的 SFTP 上傳方式。未來若要改成 git-based deploy，可考慮：
- 在 server 上 `git clone` ap-base
- Deploy 改為 `git pull origin main`
- 但這需要 server 上也設 SSH key 認證到 Gitea

目前保持現狀不改動，避免節外生枝。
