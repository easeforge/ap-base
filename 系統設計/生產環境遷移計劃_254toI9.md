## 3. 遷移步驟

### Phase 1：I9 Ubuntu 安裝（預估 2 小時）

```
□ 1.1 備份 I9 現有 Windows 資料（如需保留）
□ 1.2 安裝 Ubuntu 24.04 LTS Server
     - 磁碟分割：/ 100GB, /data 剩餘空間, swap 8GB
     - 網路：設定固定 IP（建議 10.1.0.XXX）
     - SSH：啟用，加入 public key
□ 1.3 安裝 Docker + Docker Compose
     - apt install docker.io docker-compose-v2
     - 加入 porsche 使用者到 docker 群組
□ 1.4 安裝 NVIDIA 驅動 + NVIDIA Container Toolkit
     - RTX 4060 驅動
     - nvidia-container-toolkit（讓 Docker 容器使用 GPU）
□ 1.5 安裝 Ollama
     - curl -fsSL https://ollama.com/install.sh | sh
     - 下載模型：ollama pull qwen2.5:7b && ollama pull llama3.1:8b
□ 1.6 基礎設定
     - 時區：Asia/Taipei
     - 防火牆：ufw 設定
     - NTP 同步
```

### Phase 2：Docker 容器遷移（預估 4-6 小時）

```
□ 2.1 在 254 上打包所有設定檔
     tar czf /tmp/docker-migration.tar.gz \
       /home/porsche/traefik \
       /home/porsche/P-PA6.4 \
       /home/porsche/network-mgmt \
       /home/porsche/nextcloud \
       /home/porsche/onlyoffice \
       /home/porsche/hr-backend \
       /home/porsche/hr-portal \
       /home/porsche/vmis \
       /home/porsche/docker \
       /home/porsche/tenants \
       /home/porsche/services

□ 2.2 匯出 Docker Volumes
     # 列出所有 volumes 並逐一備份
     for vol in $(docker volume ls -q); do
       docker run --rm -v $vol:/data -v /tmp/vol-backup:/backup \
         alpine tar czf /backup/$vol.tar.gz -C /data .
     done

□ 2.3 傳輸到 I9
     scp /tmp/docker-migration.tar.gz porsche@I9-IP:/home/porsche/
     scp /tmp/vol-backup/*.tar.gz porsche@I9-IP:/tmp/vol-backup/

□ 2.4 在 I9 上還原
     # 還原設定檔
     cd /home/porsche && tar xzf docker-migration.tar.gz

     # 還原 Docker Volumes
     for f in /tmp/vol-backup/*.tar.gz; do
       vol=$(basename $f .tar.gz)
       docker volume create $vol
       docker run --rm -v $vol:/data -v /tmp/vol-backup:/backup \
         alpine tar xzf /backup/$vol.tar.gz -C /data
     done

□ 2.5 匯出/匯入資料庫
     # PostgreSQL
     ssh porsche@254 "docker exec hr-postgres pg_dumpall -U postgres" > pg_dump.sql
     cat pg_dump.sql | docker exec -i I9-postgres psql -U postgres

□ 2.6 逐一啟動 Compose 專案
     # 按順序啟動（基礎設施優先）
     cd ~/services/redis && docker compose up -d
     cd ~/traefik && docker compose up -d
     cd ~/services/keycloak && docker compose up -d
     cd ~/services/mailserver && docker compose up -d
     cd ~/nextcloud && docker compose up -d
     cd ~/onlyoffice && docker compose up -d
     # ... 其餘專案

□ 2.7 兩邊並行運作
     - 254 不停機，I9 獨立運行
     - 此時 I9 使用臨時 IP，不影響 254
```

### Phase 3：驗證測試（預估 1-2 天）

```
□ 3.1 逐一檢查所有容器狀態
     docker ps --format "table {{.Names}}\t{{.Status}}"
     # 確認所有容器都是 Up 且 healthy

□ 3.2 功能驗證清單
     □ Traefik Dashboard — 可存取
     □ PA6.4 — 登入、基本操作
     □ Nextcloud — 各租戶登入、檔案存取
     □ OnlyOffice — 文件開啟編輯
     □ Keycloak — 登入、SSO
     □ Mail — 收發信件
     □ Gitea — push/pull
     □ HR 系統 — 登入、查詢
     □ VMIS — 登入、查詢
     □ SCIRS — 登入
     □ PCDM — 登入
     □ Redis — 連線測試
     □ PostgreSQL — 資料完整性
     □ Ollama — API 回應（curl http://localhost:11434/api/tags）

□ 3.3 效能比較
     - I9 vs 254 的回應速度
     - RAM 使用率
     - CPU 負載
```

### Phase 4：回退方案定義

```
回退條件（任一觸發即回退）：
  □ 核心服務無法啟動（Traefik, Keycloak, Mail）
  □ 資料遺失或損壞
  □ SSL 憑證問題導致 HTTPS 失敗
  □ 效能嚴重劣化

回退步驟：
  1. 將 I9 的 IP 改回臨時 IP
  2. 將 254 的 IP 恢復（如有變更）
  3. 254 上的服務本來就沒停，直接恢復運作
  4. DNS 紀錄切回 254（如有變更）

回退時間預估：15 分鐘（只需改 IP）

重要：254 上的容器在觀察期結束前不得停止或刪除
```

### Phase 5：DNS / Traefik 切換（預估 30 分鐘）

```
□ 5.1 IP 切換方式（二選一）

     方式 A（推薦）：IP 交換
       - I9 改為 10.1.0.254
       - 254 改為其他 IP（如 10.1.0.253）
       - 所有服務零改動，DNS 也不用改

     方式 B：DNS 切換
       - I9 使用新 IP（如 10.1.0.100）
       - 修改 DNS 紀錄指向新 IP
       - 需要等 DNS 傳播

□ 5.2 切換步驟（方式 A）
     # 同時操作，約 30 秒中斷
     # 在 254 上：
     sudo ip addr del 10.1.0.254/24 dev enp2s0
     sudo ip addr add 10.1.0.253/24 dev enp2s0

     # 在 I9 上：
     sudo ip addr add 10.1.0.254/24 dev <NIC>
     # 或修改 netplan 設定後 apply

□ 5.3 切換後驗證
     - 從外部存取所有服務
     - 確認 SSL 憑證正常
     - 確認 Gitea webhook 正常
```

### Phase 6：觀察期（3-7 天）

```
□ 6.1 每日檢查
     □ 所有容器運行狀態
     □ RAM/CPU 使用率
     □ 磁碟空間
     □ 錯誤日誌
     □ 使用者回報

□ 6.2 觀察期結束條件
     □ 連續 3 天無異常
     □ 所有功能驗證通過
     □ 效能穩定
     □ 無使用者回報問題

□ 6.3 正式確認不退回
     □ 書面確認（日期 + 簽核）
     □ 才可進入 Phase 7
```

### Phase 7：254 重整為掃描平台（預估 2 小時）

```
□ 7.1 停止 254 上所有舊容器
     docker stop $(docker ps -q)
     docker system prune -a --volumes  # 清除所有

□ 7.2 移除 Ollama
     sudo systemctl stop ollama
     sudo systemctl disable ollama

□ 7.3 部署掃描平台
     - SonarQube (Port 9000)
     - DefectDojo (Port 8080)
     - 共用 PostgreSQL
     - 掃描執行器

□ 7.4 設定 Gitea Webhook
     - 連接 I9 上的 Gitea → 254 掃描平台

□ 7.5 驗證掃描功能
     - 觸發一次 Base AP 掃描
     - 確認報告產出
```

## 5. 風險與緩解

| 風險 | 影響 | 機率 | 緩解措施 |
|------|------|------|---------|
| Docker Volume 遷移遺漏 | 資料遺失 | 中 | 遷移前完整列出 volumes，逐一備份驗證 |
| SSL 憑證失效 | HTTPS 中斷 | 低 | 備份 Let's Encrypt 目錄，切換後立即測試 |
| 資料庫遷移不完整 | 功能異常 | 中 | pg_dumpall 完整備份，還原後比對 row count |
| Docker Network 名稱衝突 | 容器互連失敗 | 低 | 使用相同的 compose 檔，網路自動建立 |
| I9 硬體不穩定 | 服務中斷 | 低 | 觀察期 7 天驗證，254 保留回退能力 |
| GPU 驅動問題 | Ollama 無法使用 | 中 | 提前測試 NVIDIA 驅動 + Container Toolkit |
